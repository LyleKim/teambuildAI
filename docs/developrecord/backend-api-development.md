# 백엔드 개발 기록 — REST API·로직·DTO·CORS·Swagger 검증기

## 시작하며

프론트엔드는 changmin0293님이 디자인하고 구현한 화면을 기준으로 받았다. 화면과 상호작용 흐름이 먼저 확정돼 있었기 때문에, 나는 그 화면이 실제로 필요로 하는 데이터 모양과 흐름을 역으로 추적하면서 백엔드를 설계하고 검증하는 방식으로 작업을 진행했다. 단순히 "동작하는 API"를 만드는 것에서 그치지 않고, 이 프로젝트가 실제 서비스로 나갈 것을 전제로 REST API 설계 원칙, 로직과 뷰의 책임 분리, DTO(시리얼라이저)의 형태, CORS 설정, 예외 처리 방식, 그리고 API 문서화까지 하나씩 점검하면서 코드 품질을 끌어올리는 작업을 별도로 진행했다. 이 문서는 그 검증 과정에서 실제로 무엇을 확인했고, 어떤 문제를 발견했으며, 왜 그렇게 고쳤는지를 순서대로 기록한 것이다.

검증은 세 단계로 나눠서 진행했다. 첫 번째는 REST API 설계 원칙 자체를 지키고 있는지(URL이 자원을 표현하는지, HTTP 메서드가 역할에 맞게 쓰이는지, 멱등성이 지켜지는지), 두 번째는 로직/뷰/리소스/DTO/CORS/예외 처리가 실제 코드 수준에서 안전하고 일관적인지, 세 번째는 이 모든 걸 Swagger, OpenAPI로 문서화해서 남길 수 있는지였다. 순서를 이렇게 잡은 이유는, 설계 원칙이 흔들린 상태에서 문서부터 만들면 잘못된 계약을 그대로 문서화하는 꼴이 되기 때문이다. 구조를 먼저 바로잡고, 그다음에 그 구조를 문서로 굳히는 순서가 맞다고 판단했다.

개발은 AI에게 위의 원칙들(REST API/로직/뷰/리소스/DTO/CORS 등)을 지키며, Claude Sonnet 모델로 초기 개발을 진행하였으며, 이후 검증 과정을 거쳤다.(학습 목적)  

## 1단계 — REST API 설계 원칙 검토

가장 먼저 확인한 것은 URL이 정말 "자원(resource)"을 가리키고 있는지, 그리고 "행위"는 전부 HTTP 메서드가 담당하고 있는지였다. `config/api_urls.py`를 기준으로 앱별 URL 구조를 훑어봤는데, 대부분은 `/hackathons/`, `/coffeechats/`, `/notifications/`처럼 명사 중심으로 잘 짜여 있었다. 다만 `coffeechat` 앱에서 한 가지 구조적인 문제를 발견했다. 같은 자원인 커피챗 하나를 조회하는 URL(`/coffeechats/{id}/`)과 삭제하는 URL(`/coffeechats/{id}/delete/`)이 서로 다른 경로로 분리되어 있었던 것이다. DELETE라는 HTTP 메서드 자체가 이미 "삭제"라는 의미를 담고 있는데, 거기에 다시 `/delete/`라는 동사를 URL에 얹어놓은 셈이라 자원 중심 설계 원칙에 어긋난다고 판단했다. 이 부분은 `CoffeeChatDetailView`를 `RetrieveDestroyAPIView`로 합쳐서, URL 하나가 GET과 DELETE를 모두 처리하도록 정리했다.

두 번째로는 HTTP 상태 코드가 실제 동작과 맞아떨어지는지를 봤다. 리뷰 작성이나 참가자 수동 추가처럼 "있으면 수정하고 없으면 생성하는" upsert 패턴을 쓰는 엔드포인트들이 있었는데, 이 엔드포인트들이 실제로 새로 생성됐는지 기존 걸 덮어썼는지와 무관하게 항상 같은 상태 코드를 반환하고 있었다. REST 관례상 새로 생성된 경우에는 201, 기존 자원을 수정한 경우에는 200을 돌려주는 게 맞다고 보고, `update_or_create`가 돌려주는 `created` 플래그를 활용해서 상태 코드를 분기하도록 고쳤다.

세 번째, 그리고 가장 신경 쓴 부분은 멱등성이었다. GET,PUT,DELETE는 원래 여러 번 호출해도 같은 결과를 내야 하는 메서드이고, PATCH도 상태 전이를 다루는 경우라면 같은 원칙을 지키는 게 실무적으로 안전하다. 그런데 커피챗의 수락(`accept`), 거절(`reject`), 진행상태 변경(`progress`) 엔드포인트를 살펴보니, 이미 처리된 상태에 대해 같은 요청이 다시 들어오면 에러를 던지도록 짜여 있었다. 예를 들어 이미 수락된 커피챗에 대해 수락 요청을 한 번 더 보내면 400 에러가 나는 구조였는데, 이건 프론트에서 더블클릭을 하거나 네트워크가 불안정해서 요청이 재시도되는 상황을 그대로 사용자 에러로 노출시키는 셈이었다. 그래서 "이미 그 상태에 도달해 있다면 에러 대신 현재 상태를 그대로 200으로 돌려준다"는 원칙으로 세 엔드포인트를 전부 고쳤다. 다만 서로 다른 상태 사이를 잘못 오가려는 요청(예: 이미 거절된 걸 수락하려는 시도)까지 허용하면 안 되기 때문에, 그런 경우는 여전히 400을 유지하도록 구분해서 처리했다.

## 2단계 — 로직,뷰/DTO/CORS/예외 처리 검토

이 단계에서는 코드 하나하나를 좀 더 깊이 들여다봤다. 먼저 로직과 뷰의 책임이 잘 나뉘어 있는지를 봤는데, `notifications/services.py`의 `notify()`나 `reviews/services.py`의 `review_summary()`처럼 여러 앱이 공유하는 규칙은 이미 서비스 함수로 분리되어 있어서 이 부분은 특별히 손댈 게 없었다. 대신 실제로 심각한 문제를 하나 발견했는데, `accounts/views.py`의 `MemberProfileView`가 비공개(`is_private`) 설정을 전혀 검증하지 않고 있었다는 점이다. AI 추천 목록을 만드는 로직에서는 비공개로 설정한 사람을 확실히 제외하고 있었는데, 정작 다른 사람의 프로필을 직접 조회하는 API(`/users/{id}/profile/`)는 `user_id`만 알면 비공개 여부와 무관하게 누구나 열람할 수 있는 상태였다. 추천 목록에서는 숨겨지지만 프로필 상세 API로는 그대로 뚫려 있게 구현된 셈이었다. 이 문제를 고치면서 "비공개 프로필을 직접 조회하려 하면 어떻게 반응해야 하는가"도 함께 정리했는데, 존재 여부 자체를 숨기는 게 맞다고 판단해서 403이 아니라 404를 돌려주도록 했다. 같은 원칙을 커피챗 신규 신청(`to_user_id`)에도 적용해서, 아직 아무 관계도 없는 사람이 비공개 프로필을 대상으로 새로 접촉을 시도하는 경로도 막았다.

CORS 설정도 이 단계에서 다시 봤다. `config/settings.py`의 `CORS_ALLOWED_ORIGINS`가 `DJANGO_ALLOWED_HOSTS`나 `DJANGO_DEBUG`와 다르게 환경변수가 아니라 코드에 직접 박혀 있었고, 값도 로컬 개발 주소(`localhost:8443`) 하나뿐이었다. 이 값은 카카오 로그인 리다이렉트 URI 화이트리스트(`FRONTEND_ORIGINS`)로도 재사용되는, 보안적으로 중요한 설정이다. 실제 배포 도메인이 생겼을 때 이 값을 바꾸려면 소스코드를 직접 고쳐야 한다는 뜻이었고, 이는 다른 환경별 설정과 일관성이 없었다. 그래서 `ALLOWED_HOSTS`와 같은 패턴으로 콤마 구분 환경변수(`CORS_ALLOWED_ORIGINS`)로 빼서, 배포 환경마다 `.env` 값만 바꾸면 되도록 정리했다.

예외 처리는 두 가지 문제를 발견했다. 하나는 에러 응답의 형태가 코드를 작성한 방식에 따라 제각각이었다는 점이다. `raise ValidationError('문자열')`로 던진 에러는 응답 바디가 배열(`["메시지"]`)로 나가고, `raise ValidationError({'field': '메시지'})`로 던진 에러는 딕셔너리(`{"field": ["메시지"]}`)로 나가고 있었다. 이걸 소비하는 프론트 코드 입장에서는 API 에러 응답에 정해진 규격이 없는 셈이었다. 그래서 DRF의 `EXCEPTION_HANDLER`를 커스텀으로 등록해서(`config/exceptions.py`), 어떤 방식으로 예외를 던지든 응답에 항상 `detail` 키가 포함되도록 통일했다. 기존에 프론트가 참조하고 있던 필드별 키(`not_member` 등)는 그대로 살려뒀기 때문에 기존 로직을 깨뜨리지 않으면서 형태만 통일할 수 있었다. 다른 하나는 로깅이 프로젝트 전체에 단 한 줄도 없었다는 점이다. 이 지점에 `logger.exception(...)`을 추가하고, `config/settings.py`에 콘솔로 출력되는 `LOGGING` 설정을 새로 넣어서 컨테이너 로그로 원인을 확인할 수 있게 만들었다.

## 3단계 — Swagger, OpenAPI 문서화

마지막 단계는 API 문서화였다. 이 프로젝트는 `drf-spectacular`를 도입하기 전까지 API 문서가 전혀 없는 상태였다. `drf-spectacular`를 선택한 이유는 DRF 생태계에서 사실상 표준으로 자리 잡았고, 오래된 `drf-yasg`보다 유지보수가 활발하기 때문이다. 도입 자체는 패키지를 추가하고 `INSTALLED_APPS`와 `REST_FRAMEWORK` 설정에 몇 줄을 더하는 것으로 끝났지만, 실제로 스키마를 생성해보니 예상치 못한 문제가 있었다. `serializer_class`가 붙어 있는 제네릭 뷰들은 자동으로 문서에 잡히는데, `request.data.get(...)`으로 직접 파싱하는 순수 `APIView` 27개는 drf-spectacular가 요청·응답 형태를 추측할 방법이 없어서 문서에서 통째로 빠져 있었다. 로그인, 커피챗 수락 및 거절, 알림, 프로필 저장처럼 실질적으로 중요한 엔드포인트 대부분이 여기 해당했기 때문에, 이대로 두면 문서로서 의미가 없다고 판단해서 27개 뷰 전부에 `@extend_schema`로 요청, 응답 형태를 직접 명시하는 작업을 했다. 최종적으로 `/api/docs/`(Swagger UI), `/api/redoc/`(ReDoc), `/api/schema/`(OpenAPI 원본)를 인증 없이 열람 가능하게 등록해서, 프론트 쪽에서도 백엔드 코드를 읽지 않고 API 계약을 확인할 수 있게 만들었다.

## 에이전트 엔지니어링
본 개발 과정의 중간쯤부터 '에이전트 엔지니어링'을 학습하여
프롬프트 엔지니어링 - 컨텍스트 엔지니어링 - 하네스 엔지니어링 - 루프 엔지니어링 - 그래프 엔지니어링을 학습하여 적용시켰다.
특히 UI를 frontend-design 스킬로 리펙토링하는 과정에서 아래와 같은 방법을 사용했다.

1. superpower 스킬을 사용하여 플랜 파일의 작성
2. 플랜 내 TDL 중 서브 에이전트 사용 및 병렬 처리 가능 여부 확인 및 병렬 기반 서브에이전트 운영 계획 설립(컨텍스트 오염 방지)
3. 서브에이전트 완료 기준을 "절차 수행"에서 "목적 달성 확인"으로 명시 및 루프 적용
4. 각 서브에이전트 작업 완료 시 1.에서 만든 플랜 파일 내의 TDL 목록 체크 및 진행 내용 기록을 수행하게 하여 상태(state)의 중앙 집중화

이 과정을 통해서 프롬프트에서 그래프까지 에이전트 엔지니어링을 적극적으로 사용하여 구현하였다.

결과 눈에 보이는 품질은 양호하게 작성되었으며, 서브에이전트를 사용하여 컨텍스트 오염을 피함으로써 에이전트의 목적의 벗어난 동작을 막을 수 있었다.  
또한 서브에이전트의 루프 설정 결과 목표 달성까지 문제를 해결 및 기록하는 모습을 볼 수 있었다.  
이를 통해서 **양질의 품질과 비정상적 에이전트 활동에 따른 추가 토큰 소모**를 막을 수 있었다.  

## 돌아보며

이 세 단계를 거치면서 느낀 건, "일단 동작하니까 됐다"와 "이 API가 실제로 안전하고 일관적인가"는 완전히 다른 기준이라는 점이었다. 특히 `is_private` 검증 누락이나 에러 응답 형태 불일치처럼, 눈에 보이는 기능 테스트로는 잘 드러나지 않는 문제들이 이런 원칙 중심의 재점검 과정에서 발견됐다.  
앞으로의 개발에서는 에이전트 엔지니어링 기법을 적용, 초기에 구체적인 계획 하에 개발을 적용시켜 '토큰노믹스' 목적을 달성하면서 품질 좋은 서비스를 개발해야겠다.
