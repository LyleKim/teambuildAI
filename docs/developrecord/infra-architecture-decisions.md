# 인프라 설계 기록 — EC2·RDS·S3·서브넷 구성을 고민한 과정

## 시작하며

원래 계획했던 다음 작업은 해커톤 정보를 자동으로 모아오는 크롤링 파이프라인이었다. 크롤러가 데이터를 긁어서 S3에 올리고, Lambda가 그걸 비동기로 처리해서 RDS와 S3에 최종 데이터를 채워 넣는 구조를 구상하고 있었는데, 막상 설계를 시작해보니 구성 요소가 많아서 실제로 완성하기까지 꽤 오래 걸릴 것 같다는 판단이 들었다. 그래서 순서를 바꿔서, 크롤링 파이프라인처럼 복잡한 걸 만들기 전에 먼저 teambuildAI 애플리케이션 자체를 AWS에 실제로 배포할 수 있는지부터 검증하기로 했다. 데이터를 자동으로 채우는 문제와 서비스를 배포하는 문제는 서로 다른 문제이고, 후자를 먼저 검증해두면 나중에 크롤링 파이프라인을 붙일 때도 어떤 인프라 위에 얹을지가 명확해지기 때문이다.

## CloudFront 대신 EC2(nginx)를 선택한 이유

배포 아키텍처를 고민하면서 가장 먼저 결정해야 했던 건 정적 파일을 어떻게 전달할 것인가였다. 흔한 선택지는 CloudFront 같은 CDN을 앞에 두는 것이지만, CDN의 핵심 가치는 여러 리전에 흩어진 사용자에게 지연 시간을 줄여주는 데 있다. 이 프로젝트는 아직 멀티 리전 트래픽을 고려할 단계가 아니었고, 정적 페이지를 전달하는 것 자체가 목적이라면 nginx 하나로도 충분하다고 판단했다. 그래서 처음에는 "CDN 캐싱이 필요 없다면 CloudFront 없이 nginx로 가는 게 낫지 않을까"라는 질문에서 출발했다.

다만 CDN 성능과 무관하게 CloudFront를 쓰는 흔한 이유가 하나 더 있다는 것도 함께 고려했다. TLS 인증서 관리다. 카카오 로그인은 HTTPS가 필수이기 때문에 인증서가 반드시 필요한데, CloudFront와 ACM을 쓰면 인증서 발급과 자동 갱신을 신경 쓸 필요가 없어진다. 반대로 nginx를 직접 쓰면 EC2에 certbot을 설치하고 90일마다 자동 갱신되는지까지 관리해야 하는 부담이 생긴다. 이 갈림길에서 나는 학습을 목적으로 일부러 더 손이 가는 쪽을 선택했다. TLS 인증서 관리, 정적 페이지 서빙, 리버스 프록시까지 전부 nginx가 직접 처리하도록 구성해서, 인프라를 다른 서비스 뒤에 숨기지 않고 직접 다뤄보기로 한 것이다. 그 결과로 최종 아키텍처는 `nginx(EC2) → WAS(EC2, gunicorn) → RDS + S3` 구조로 확정됐다.

## 처음에는 비용 때문에 서브넷을 나누지 않았다

아키텍처를 처음 Terraform으로 옮길 때는 비용을 최우선으로 고려했다. "정석"대로라면 WAS와 RDS는 프라이빗 서브넷에 두고 NAT Gateway를 거쳐서만 외부와 통신하게 만드는 게 맞다. 하지만 NAT Gateway는 시간당 과금이 붙는 리소스라서, 학습 목적의 실험 단계에서 월 3만 원 이상의 고정비를 감수할 실익이 없다고 판단했다. 그래서 첫 버전은 EC2 세 대(정확히는 nginx와 WAS 두 대)와 RDS를 전부 하나의 퍼블릭 서브넷에 두고, 대신 보안그룹만으로 계층을 나누는 구조로 설계했다. nginx의 보안그룹은 80·443·22번 포트를 열어두고, WAS의 보안그룹은 nginx의 보안그룹에서 오는 8000번만 허용하고, RDS의 보안그룹은 WAS의 보안그룹에서 오는 3306번만 허용하는 식이었다. 서브넷 자체는 인터넷 게이트웨이로 가는 라우팅이 열려 있지만, 보안그룹이 인바운드를 촘촘하게 막아주면 실질적인 보호는 충분하다고 봤다.

## floci를 알게 되면서 바뀐 것

이 구성을 실제 AWS에 올리기 전에 로컬에서 검증해보고 싶다는 생각이 들었는데, 마침 다른 프로젝트에서 클라우드 요금이 예상보다 많이 나오고 있어서 비용 걱정 없이 검증할 방법이 필요했다. 이때 알게 된 게 `floci`라는 로컬 AWS 에뮬레이터였다. 처음에는 LocalStack과 비슷한 도구일 거라고 짐작했는데, 실제로 리소스를 만들어보면서 능력을 검증해보니 예상보다 훨씬 실제에 가까웠다. `floci`가 만드는 EC2 인스턴스는 상태만 흉내 내는 API 껍데기가 아니라 실제 Docker 컨테이너였고, RDS도 정말 접속해서 쿼리를 돌릴 수 있는 MySQL 엔진이었다. 반면 VPC·서브넷·보안그룹으로 표현되는 네트워크 격리는 전혀 강제되지 않는다는 것도 직접 테스트해서 확인했다. 아무 보안그룹 권한도 없는 인스턴스가 다른 서브넷의 8000번, 22번 포트에 자유롭게 접속되는 걸 보고, "이 도구로는 기능이 진짜로 동작하는지는 확인할 수 있지만, 보안 경계가 실제로 작동하는지는 확인할 수 없다"는 결론을 내렸다.

이 사실이 오히려 설계를 더 정석에 가깝게 바꾸는 계기가 됐다. 로컬 검증에는 비용이 들지 않으니, 이번 기회에 처음 미뤄뒀던 프라이빗 서브넷과 NAT Gateway 구성을 제대로 만들어보기로 한 것이다. VPC 안에 퍼블릭 서브넷 두 개와 프라이빗 서브넷 두 개를 두고, nginx와 NAT Gateway는 퍼블릭 서브넷에, WAS와 RDS는 프라이빗 서브넷에 배치했다. WAS는 퍼블릭 IP를 아예 받지 않도록 설정했고, RDS도 `publicly_accessible = false`로 막았다. 관리자가 WAS에 SSH로 접속해야 할 때는 nginx를 점프 호스트로 거치도록 설계했다. 덤으로 프라이빗 서브넷에서 S3로 나가는 트래픽이 NAT Gateway를 거치지 않고 AWS 백본으로 바로 나가도록 S3용 VPC 게이트웨이 엔드포인트도 추가했는데, 이건 실무에서 자주 놓치는 비용 최적화 포인트라서 학습 삼아 정석대로 넣어봤다.

이 구성을 `floci` 위에 실제로 apply해서 WAS와 RDS가 정말 프라이빗 서브넷에 들어갔는지, 퍼블릭 IP 없이 뜨는지를 Terraform state로 직접 확인했다. nginx가 WAS의 프라이빗 IP로 리버스 프록시를 하고, WAS가 RDS에 붙어서 마이그레이션을 돌리는 것까지 전부 실제로 동작하는 걸 검증했다. 다만 이 검증은 어디까지나 "구성 요소들이 서로 잘 연결되는가"를 확인한 것이지, "보안그룹이 정말 외부 접근을 막아주는가"는 `floci`가 원천적으로 확인해줄 수 없는 부분이라는 걸 분명히 해뒀다. 그래서 이 부분만큼은 나중에 실제 AWS 프리티어에 짧게 올려서 최종적으로 확인하고, 확인이 끝나면 바로 `terraform destroy`로 정리하는 것을 남은 과제로 남겨뒀다.

## 검증 과정에서 발견한 예상 밖의 버그

`floci` 위에서 실제로 소프트웨어를 설치하고 붙여보는 과정에서, 설계 단계에서는 전혀 예상하지 못했던 버그를 하나 발견했다. WAS 컨테이너에 Django를 설치하고 `migrate`를 돌렸더니 `MySQL 8.4 or later is required (found 8.0.46)`라는 에러가 났다. 확인해보니 Django 6.x부터 MySQL 백엔드가 지원하는 최소 버전이 8.4로 올라갔는데, 정작 내가 Terraform으로 설계한 RDS는 비용과 안정성을 생각해서 8.0으로 지정해뒀던 것이다. 로컬 실험 환경이 아니라 실제 배포 코드에 그대로 들어있었다면 배포 직후 마이그레이션이 100% 실패했을 문제였다. 이 문제는 Django 쪽 버전을 낮추는 방법도 있었지만, 최신 프레임워크 버전을 유지하는 게 더 낫다고 판단해서 RDS의 `engine_version`을 8.4로 올리는 쪽으로 해결했다. 이 사례는 로컬 에뮬레이터로 실제 소프트웨어를 설치하고 동작시켜보는 검증이 왜 필요한지를 보여주는 사례라고 생각한다. Terraform 코드만 봐서는 절대 알 수 없는, 애플리케이션 계층과 인프라 계층 사이의 버전 호환성 문제였기 때문이다.

## gunicorn 도입

인프라를 설계하면서 함께 정리한 게 하나 더 있다. 기존에는 Django의 개발 서버(`manage.py runserver`)를 Docker 컨테이너의 실행 명령으로 그대로 쓰고 있었는데, 이건 단일 스레드로 동작하고 동시 요청을 제대로 처리하지 못해서 Django 공식 문서에서도 프로덕션 사용을 명시적으로 금지하는 방식이다. WAS 역할을 하는 EC2가 실제로 여러 요청을 동시에 처리해야 하는 이상, 이 부분을 그대로 둘 수는 없었다. 그래서 상용 WSGI 서버인 gunicorn을 패키지에 추가하고, `Dockerfile`의 기본 실행 명령을 `gunicorn config.wsgi:application`으로 바꿨다. 다만 로컬 개발 환경(`docker-compose.yml`)에서는 코드를 고칠 때마다 자동으로 반영되는 `runserver`의 편의성이 여전히 필요하다고 판단해서, 로컬 개발용 compose 설정은 그대로 두고 이미지 자체의 기본값만 gunicorn으로 바꾸는 방식으로 두 가지 목적을 분리했다.

## 돌아보며

이번 인프라 작업을 하면서 가장 크게 느낀 건, "정석대로 설계하는 것"과 "지금 당장 그 정석을 적용할 수 있는가"는 다른 문제라는 점이었다. 비용 제약이 있을 때는 SG 중심의 단순한 구조로 시작하고, 그 제약이 사라지는 조건(이번 경우엔 무료 로컬 에뮬레이터)을 찾으면 그때 정석 구조로 옮겨가는 단계적 접근이 실제로는 더 합리적이었다. 그리고 로컬 에뮬레이터가 아무리 실제와 비슷해도 검증할 수 있는 범위에는 한계가 있다는 것, 그래서 그 한계가 어디인지를 미리 파악해두고 마지막에 진짜 클라우드로 한 번은 확인해야 한다는 것도 이번 과정에서 얻은 교훈이다.

### NGINX
#### 웹소켓  
리버스 프록시 역할을 하는 것은 기본이고, 
웹소켓에 대해서도 하는 역할이 있다. WebSocket Proxy 역할이다.  
기본적으로 http 통신은 클라이언트의 요청을 처리하고 연결을 종료한다. 그러나 웹소켓은 그러면 안된다. 따라서 HTTP GET 요청으로 시작하지만 지속적인 양방향 TCP 연결로 전환할 필요가 있다. 클라이언트에서 웹소켓으로 유지하기 위한 upgrade 관련 헤더를 nginx는 기본 무시하기 때문에, 명시적으로 설정을 넣어줘야한다.
```
# WebSocket 업그레이드가 지원되는 HTTP/1.1 사용
proxy_http_version 1.1;  

# 클라이언트가 요청한 Upgrade 헤더 전달
proxy_set_header Upgrade $http_upgrade;  

# Connection 헤더를 "upgrade"로 고정
proxy_set_header Connection "upgrade";
```
이렇게 하여 해당 헤더를 WAS로 온전히 전달하고, 커넥션 유지를 해준다.  
#### SSL/TLS
현대 대부분의 통신에서 L6 보안은 SSL/TLS를 적용하여 http의 평문을 암호화한다.  
이러한 구성을 위해서 NGINX가 암호화와 복호화를 담당한다.  
들어오는 요청에 대해서 TLS를 벗겨서 HTTP로 만들어 WAS로 전달하고, WAS에서 만든 HTTP 헤더와 평문을 SSL/TLS로 암호화하여 클라이언트에게 전달한다.
이 모든 암,복호화 과정을 NGINX가 담당하는 것은 SSL/TLS의 연산이 CPU를 많이 소모하기 때문이다. 그래서 이 무거운 연산을 NGINX가 담당하게 하고, WAS는 비즈니스 로직에 집중하라고 한 것이다.(실제로 WAS쪽 서버의 부하가 높다고 직무 부트 캠프에서 이야기를 들었다.) 그래서 클라이언트와 NGINX, WAS의 구성은 아래와 같다.
```
[클라이언트] --(HTTPS/443)-> [NGINX] --(HTTP/80)-> [WAS]
```
그런데 여기까지의 아름다운 이야기에 문제가 발생한다. WAS는 HTTP의 헤더와 평문을 작성하는 역할을 담당하는데, 기본 요청이 http이면 응답도 http이어야한다가 서버 클라이언트 구성의 기본이다. nginx에서 요청이 http니 was도 http로 헤더와 평문을 작성해서 nginx에게 보낸다.  
nginx가 tls 암호화를 하겠지만, 최종 응답을 받는 클라이언트가 tls를 복호화했더니 응답 내용이 http면 해당 내용을 거절하게 된다. 이러한 문제를 막기 위해서 NGINX에서 WAS에게 요청을 넘기기 전에 "내 요청은 http지만 너는 응답할 때 https로 생각하고 진행해라"라는 설정을 해줄 필요가 있다. 요즘 tls 암호화는 기본적으로 적용되기 때문에 반드시 필요한 절차이다.
